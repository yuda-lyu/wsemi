# 處理要點

本檔記 wsemi 業務端之特化要求與其處理流程(使用者裁示之處理偏好),新增之項附於末;2026-11-22 新建,首批自本套件之 Claude Code 自動記憶提取(自動記憶依資料夾路徑存放,路徑更名即失聯;sgud 優先).「修退化先追既有原則」見 `sgud/exp/experience_20261028.md`,收錄判準見 `sgud/rule/rulebook.md` R-SCOPE-01,破壞性變更依專案原則 14 記入 `sgud/rule/rulebook_breaking*.md`.

## 1. 版本與發布是使用者的事: 不拿邊角差異逼使用者決定 semver

- 依據: 2026-09-22 新增 `domDragPointer` 並把 `domDragBarAndScroll` 改建其上時,agent 把提案自列之 14 項邊角差異升格為「破壞性改動、至少 minor 或 major」,反覆要使用者拍板版本政策;使用者明確表示「我原本就是要擴充」.2026-10-17 再申: 使用者不想被逼決 semver,僅問「是否修」與「順序」.
- 處理: ①先以並排實測量差異(同一組真操作跑現行與提案,逐情境比對,見 `sgud/exp/experience_20261122.md` 〈domDragBarAndScroll 兩輪…〉),再定性為「邊角修正」或「破壞性變更」;②回報只陳述行為差異與下游影響,不要求使用者裁示版本號;版本與發布由使用者與主控決定;③確屬破壞性者依專案原則 14(不做舊版相容)記入〈破壞性變更紀錄〉.

## 2. 回報須分清「既有行為」與「本次改動」

- 依據: 2026-10-11 實作 `detectXSS` 時,agent 順帶發現既有缺陷(`clearXSSDyn` 於不預載 xss 時拋 `t is not a function`、`clearXSS` 只找全域 `xss`)並一併修正,回報未明講,使用者誤以為是本次修正造成.
- 處理: 回報中凡「順帶發現」者逐項標明屬「既有行為(未改)」「既有缺陷(本次一併修)」或「本次新增／改動」,與主體改動分列;該次之既有行為例: js-xss 擋 `pics/a.png` 類相對路徑、`a<b 且 c>d` 被當標籤,判定不需修(見 `rulebook_xss.md` R-XSS-01 已知限制).

## 3. 收到建議書或提案: 先逐條核對屬實再動工,並補能抓到同類問題之測試

- 依據: 使用者 2026-09-05(對 execCli 家族擴充提案要求「先審再做」)、2026-09-07(對 fsMergeFilesCore 失敗路徑報告要求「改,並擴充 test 使此類問題之後能被抓到」)、2026-09-13(對 evem 包裝版質疑「感覺是補破洞」).
- 處理: ①逐條核 `file:line`、以實測量過再信(報告之證據與修正 diff 皆可能有誤,不照抄);②確認主張屬實後才動工;③每個修正附能在日後抓到同類問題之測試(含修前紅);④連續修補同一功能時先問架構是否錯了(見 `experience_20261122.md` 〈事件派發之定案…〉).

## 4. 新增選項之命名: 開關類用 `use*` 前綴,名稱須能自解語意

- 依據: 2026-09-01 `cache()` 改版,選項命名走 `use*` 前綴(對齊既有 `useSync`、`useNormNewline`、`useKeyForError`),使用者退回 `useCacheError`(`cacheError` 不成名詞),定案 `useCacheWhenError`.
- 處理: 新增開關類 opt 先對齊既有命名,名稱不看文件即能知道語意;判型一律以 `isbol` 判別,非 boolean 視為未指定(K3).
