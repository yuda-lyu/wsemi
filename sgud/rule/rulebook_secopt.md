## R-HASH-TYPE-01 雜湊演算法 `opt.type`／`opt.typeHash` 為安全相關 opt: 給了而無效即拒絕(fail-closed),不改用預設

- **規則**:
  1. 雜湊演算法決定校驗值之意義,**不依 K3 改用預設**(靜默換演算法比拒絕更危險): `undefined`、`null` 為未給(取預設);給了須為**原始字串**且為允許集合之成員,否則拒絕.數字、布林、物件、陣列、`''`、包裝物件(`new String`)、不在集合之字串(含大小寫不同者如 `'MD5'`)、原型鏈名稱(`'constructor'`、`'toString'`、`'__proto__'`、`'hasOwnProperty'`)皆無效.
  2. **允許集合**: Node 端函數為注入之 `crypto.getHashes()`(以陣列 `includes` 比對,不經物件鍵查找,故原型鏈名稱不被誤判;注入之 `crypto` 無 `getHashes` 函數或其拋錯時無從核對集合,非空字串視為通過、交 `createHash` 核對),`xxhash64` 只在其路徑支援者另允許(`fsGetFileHash(Core)`、`fsGetFilesWithHashInFolder(Core)`、`fsTask`);`getFileHash`／`getFileBasicHash`(Blob,hash-wasm)為其 `kp` 之鍵(`MD5`、`SHA-1`、`SHA-256`、`SHA-384`、`SHA-512`、`md5`、`sha1`、`sha256`、`sha384`、`sha512`,`getFileHash` 另 `xxhash64`).
  3. **訊息**(V19、V20,不帶給定之值): `invalid opt.type: must be one of crypto.getHashes()`;含 `xxhash64` 之路徑 `invalid opt.type: must be 'xxhash64' or one of crypto.getHashes()`;`fsTask` 為 `invalid opt.typeHash: …`(同步拋 `Error`,先於建立紀錄資料夾與啟動計時器);`getFileHash`／`getFileBasicHash` 為 `invalid opt.type: must be one of 'MD5', 'SHA-1', …`(列其 `kp` 之鍵).
  4. **檢查於入口,先於任何讀檔、列舉、複製、刪除與連網**; 順序: 路徑參數 → 注入相依(`opt.fs`、`opt.path`、`opt.crypto`)→ type → 「是否為檔案/資料夾」.**同一函數所有路徑一致**: 資料夾無檔案時亦檢查(原空資料夾不呼叫 `createHash` 而回空雜湊),`fsSyncFolderCore` 目標資料夾不存在而整份複製(不經雜湊)時亦檢查(原同一無效 `type` 有時 reject 有時成功).
  5. 單一擁有者 `src/_chkHashType.mjs`(`chkHashType(type, { crypto, xx, list, name })` 回 `null`〔未給或有效〕或訊息字串);各站點於其後自行把 `undefined`／`null` 換成預設.
- **站點全集(16 個函數,盤點 W-08)**: `fsGetFileHashCore`、`fsGetFileBasicHashCore`、`fsGetFilesWithHashInFolderCore`、`fsGetFolderBasicHashCore`、`fsTreeFolderWithHashCore`、`fsSyncFolderCore`(單一擁有者 `chkHashType` 之呼叫端)、`fsTask`、`getFileHash`、`getFileBasicHash`、及其對外包裝 `fsGetFileHash`、`fsGetFileBasicHash`、`fsGetFilesWithHashInFolder`、`fsGetFolderBasicHash`、`fsTreeFolderWithHash`、`fsSyncFolder`(包裝只轉交,經 Core 之入口檢查);`getFileXxHash` 無 `type`(盤點列入該表係因其 `console.log` 回顯輸入值,屬 N-C 之非 fs 列,不在本批).
- **盤點指令**: `Grep "chkHashType\(" src/` 預期 10 檔(`_chkHashType.mjs` 定義 + 上列 9 個呼叫端: 6 個 `fs*Core`、`fsTask`、`getFileHash`、`getFileBasicHash`);`Grep "get\(opt, 'type'" src/` 與 `typeHash` 之讀取點皆須配對一個 `chkHashType` 呼叫.

## R-FS-ERRMSG-01 Node 原生錯誤一律改固定詞彙加錯誤碼,不回傳含路徑、網址、輸入值之原文

- **規則**(W-23 A＋C):

  4. 站點: 凡經 `toResultError` 之結果物件函數(12 個 Core: `fsWriteJson`、`fsReadTextCore`、`fsWriteTextCore`、`fsCreateFileCore`、`fsCopyFileCore`、`fsCopyFolderCore`、`fsCreateFolderCore`、`fsDeleteFileCore`、`fsDeleteFolderCore`、`fsRenameFileCore`、`fsRenameFolderCore`、`fsCleanFolderCore`,另 `fsWriteTextAtomicCore`)、字串 reject 家族之 `catch` 與串流 `error` 監聽器(`fsGetFileBasicHashCore`、`fsGetFileXxHashCore`、`fsGetFileHashCore`、`fsGetFolderBasicHashCore`、`fsGetFilesWithHashInFolderCore`、`fsTreeFolderWithHashCore`、`fsSyncFolderCore`、`fsDeleteFileSafeCore`、`fsDeleteFolderSafeCore`、`fsMergeFilesCore`、`fsDownloadFileCore`、`fsBuildWriteStreamText`、`fsGetBinManifestEntry`)、同步拋出者(`fsTreeFolderCore`、`fsEvem`)、`fsDownloadFileVerifyCore` 與 `fsEnsureBinsCore` 之 `errMsg`／`cause`.
