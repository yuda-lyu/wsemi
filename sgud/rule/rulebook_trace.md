## R-TRACE-01 計時器相關函數之觀察回調(opt.onTrace)與其測試: 以事件同步、斷言語意,不以延時偵測

- 依據: 使用者 2026-10-28 裁示(計時器相關函數以 opt 擴充觀察回調,測試以回調判斷是否正確運行,不以延時偵測);主控制式規格 `C:\opensrcOper\dspec\計時器相關函數之觀察回調與測試.md`(2026-10-28 定稿)P1～P7.緣由: 主控全套於高負載時 `test/domDetect.test.mjs`(輪詢模式)少一筆;以「等 N 毫秒後檢查」驗證計時器函數者,負載下計時器與其回呼之時差不定.
- 規則:
  1. 名稱與格式(主控 2026-10-28 核可,dspec §2 已定稿): 選項名一律 `opt.onTrace`(wsemi 之通知型回調一律 `on*` 且回傳值不用,如 `onRetry`、`onProgress`、`onLine`;`fun*` 為回傳值被使用者,如 `funWithMsg`、`funEmit`);事件為單一凍結物件 `{ type, ... }`,`type` 為各函數於 JSDoc 列舉之固定字串,其餘欄位為原始值快照(數字、字串、布林、null),不傳內部物件、陣列或 DOM 元素.**事件欄位名不得為 `type`**(保留給事件類型,會被展開覆蓋);第三方事件種類(如 chokidar 之 add/unlink/addDir)欄位名用 `kind`.
  2. 取得與呼叫之單一擁有者為 `src/getTrace.mjs` 之 `getTrace(opt)`(2026-10-28 wsemi-run07 起**由 index 對外匯出**,供他自有套件 `import { getTrace } from 'wsemi'`;原 `src/_trace.mjs` 因 `toolg/gPackageIndex.mjs` 濾掉底線開頭檔而改名): `opt.onTrace` 非函數回 null;回調同步、不帶接收者呼叫;其同步拋錯與回傳 Promise 之 rejection 皆忽略;回傳值不用.各函數不得自寫呼叫與攔截.函數原無 `opt` 者增選用參數(省略時同舊版;熱路徑如 `delay` 以 `opt ? getTrace(opt) : null` 取,未傳 opt 時不多一次取值).
  3. 呼叫站點一律 `if (trace) { trace(type, { ... }) }`,未傳回調時不組事件物件,行為、時序與效能同未支援前(P3).
  4. 事件之放置: 判定與其結果(如 domDetect 之 check 與 emit/skip、waitFun 之 result 與 resolve/reject)各為一事件,以序號或計數對應;派發使用端事件者於派發前通知(監聽器拋錯而中斷派發時仍已通知);settle 類於 resolve/reject 之前通知;釋放(clear)後不再通知.
  5. 測試:
     - 非時間規格者,以 `test/tools/timeKit.mjs` 之 `traceRec` 等第 N 個事件(`wait(pred, from, n)`)為同步點,再對事件內容與最終狀態斷言;不以 `sleep(N)` 後檢查.`wait` 之逾時(預設 20000ms)只防懸置,不表達規格.
     - 時間本身即規格者(節流窗口、防抖等待、逾時門檻與各觸發之先後)以 `useFakeClock` 推進(P5),並以觀察回調斷言事件內容.
     - 否定斷言(已停止、不得量測)之觀察窗可保留短暫真實等待,歸 B 類(負載只使窗內事件變少而漏抓,不使正確實作失敗);停止本身另以事件(如 domDetect 之 `inline` on:false)斷言.
     - 真實檔案監看類案(chokidar)步進式: 做一個檔案操作,等被測函數回報已處理該操作之事件(公開事件或 onTrace 之 `emit`),才做下一個操作;起始先等 `ready`;rename 等一個操作產生多個事件者等到預期之全部事件;整案以 `traceRec` 之 `guard` 作懸置防護.測試輔助行程等子行程就緒不得固定等 N 毫秒,改等可觀察之就緒條件(串流 `close`/`finish`、檔案已存在且確被鎖定、子行程先輸出就緒標記),條件輪詢之防懸置上限用真實計時器.
     - 子行程之懸置判定以事件為準(已過應 settle 之事件仍續行即 pending,`test/tools/pmSettleRunner.mjs` 之 `settleTrace`/`lateTick`),不以牆鐘看門狗;無事件之懸置由子行程逾時兜底(只防懸置).
     - 子行程/外部程序輸出之先後、分段與「已啟動」(wsemi-run09): 不以子行程內 `setTimeout` 隔開輸出(負載下父行程卡頓則兩段併成一個 chunk 或跨管道亂序); 改**事件閘門**——子行程輸出一段後輪詢標記檔,父行程於 onTrace 之 `data` 事件見到該段才建立標記檔放行下一段(execProcess 之合併順序與編碼切換、execCli 之 maxBuffer),使順序與分段由因果決定而非時間; 「子行程已啟動並輸出」亦以 `spawn`/`data` 事件為同步點(逾時門檻本身仍用假時鐘).驗證樹殺須孫行程 detached: Windows 下 libuv 把非 detached 之子行程放入 KILL_ON_JOB_CLOSE 之 job,只殺父亦連孫一起結束而無法分辨是否真樹殺(變異「只殺該 pid」於非 detached 時存活、detached 時被擊殺); 孫行程消失以真實計時器輪詢 `process.kill(pid, 0)` 到 ESRCH,上限只防懸置.
     - 本機真實 I/O 與假時鐘併用(下載/取得類,wsemi-run09): 假時鐘只控制計時器,真實 socket 與子行程不受控,且同行程之本機伺服器若用被 mock 之計時器決定出資料時刻會失效. 作法: 時間門檻類(stallMs、totalMs、重試間隔、停滯)改**記憶體內回應**(`ReadableStream`,由測試放行每一塊)加假時鐘,以 `headers`/`data`/`request` 等事件為同步點再推進,並以事件之虛擬時刻(`Date.now()`)斷言精確間隔(取代 `ms < N` 牆鐘門檻); 只有真實連線才有意義者(暫存檔位置、連線被關閉)保留真實伺服器,以閘門放行與伺服器端 `close` 事件為同步點.**假時鐘期間不得使用真實 undici `fetch`**(其內部計時器於還原後殘留並被後續假時鐘案誤清,實測使後案之總時限計時器整段不觸發); 伺服器加 `Connection: close` 會觸發 undici 斷言 `assert(!this.paused)` 使整個測試檔崩潰.以 `performance.now`/`hrtime` 計時者(fsDownloadFileVerifyCore 之單調時鐘案)假時鐘控制不了,以放大比例使真實耗時遠小於剩餘預算並只靠事件斷言語意.
     - 不以重試掩蓋、不只加大逾時(P6).每個改寫附變異證據(仍抓得到原本要抓之缺陷).
     - 每個加觀察回調之函數須有 P3/P4 案: 未傳、紀錄、拋錯、回傳 rejection、非函數五種之結果相同且無未處理之 rejection;事件凍結、各 type 之欄位固定.
  6. 負載試驗(P7): `test/tools/loadTrial.mjs --burners <邏輯核數>`(壓力行程於結束時終止並以 PID 回驗,另於父行程消失或逾 `--burn-max` 時自行結束);同一批測試、同次數跑改造前(以 `git archive` 解出之 HEAD 副本,`--cwd`)與改造後,比較各案失敗率.另可加 `--lag L:P`(每 P 毫秒阻塞事件迴圈 L 毫秒,可重現之延遲)作補充.
